## Comment draft for #112

Following up on the B30 line in the triage above — "not reproduced on current source
build". That is correct, and so was our earlier PARTIAL. They were measured on different
builds, and the mechanism is worth recording so B30 gets closed with the right
provenance.

**B30's remaining `<img>` case is not a `hover` defect. It is B6.**

On published v26.5.31, `hover` has no `--timeout` flag and an effective default of zero,
so it never auto-waits:

```sh
# an <img> with an external src, hovered before the bytes arrive
vibium hover "#img"
# → Error: failed to hover: timeout after 0s: visible check failed — zero size
#   (fails in ~200ms — no wait)
```

An `<img>` is simply the most common element that is *briefly* zero-size: it has no
intrinsic dimensions until it loads. A cached or already-rendered image passes; an
uncached one fails. That is why the two runs disagreed — nothing to do with `<img>`
handling specifically.

The same zero timeout affects the sibling actions, all on v26.5.31:

```
hover     → timeout after 0s: visible check failed — zero size
dblclick  → timeout after 0s: visible check failed — zero size
check     → timeout after 0s: visible check failed — zero size
focus     → succeeds (no visibility check)
scroll    → succeeds (no visibility check)

hover|focus|dblclick|check --timeout 2s  → Error: unknown flag: --timeout
```

Which matches #182's own description of the problem exactly — `hover` is named among the
~10 element-action commands that had no `--timeout` and whose daemon handlers ignored it.

**So #182 resolves B30.** `addTimeoutFlag` sets `*target = api.DefaultTimeout` rather than
zero, and the PR's tests already cover "the auto-wait path (element appears after a
delay)" on "a newly-flagged action (`hover`)" — which is precisely this scenario.

Suggested disposition: close B30 as **fixed by #182** rather than "not reproduced".
"Not reproduced" invites a reopen the next time someone hovers an uncached image on a
published build; "fixed by #182" is accurate and closes it permanently.

**Regression test worth keeping**, since it makes the zero-size window deterministic
without depending on network timing:

```js
const im = document.createElement('img');
im.id = 'b30';
document.body.appendChild(im);                    // 0x0 — no src yet
setTimeout(() => { im.src = '/img/avatar-blank.jpg?cb=' + Date.now(); }, 600);
```

```sh
vibium hover "#b30"
# v26.5.31: Error ... timeout after 0s: visible check failed — zero size  (~200ms)
# post-#182: should wait for the image to gain dimensions, then succeed
```

One note for whoever publishes: until #182 ships to npm, `npm latest` is still 26.5.31,
so this and B6, B9, B14, B18, B20, B22, B31 all still reproduce on any installed build.
