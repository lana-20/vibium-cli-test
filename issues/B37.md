# B37 — `vibium find` mints a `@ref` for a CSS selector that matched nothing

**vibium v26.5.31 · macOS darwin 25.5.0**
**Filed as:** _not yet filed_ — drafted 2026-08-07, awaiting review.
**Premise already conceded upstream:** see "Where this came from" below.

## Summary

`vibium find "<css>"` returns a usable-looking element ref and exits 0 even when the
selector matches nothing. The output embeds a raw Go `<nil>`:

```sh
vibium go https://example.com
vibium find "#nope-zzz"
# → @e1 <nil>
# exit 0
```

With `--json` it is reported as an outright success:

```sh
vibium find "#nope-zzz" --json
# → {"ok":true,"result":"@e1 <nil>"}
# exit 0
```

The failure surfaces later, at the point of use, blaming the wrong command:

```sh
vibium click "@e1"
# → Error: failed to click: timeout after 0s: element not found
# exit 1
```

**Only the CSS-selector path is affected.** Every semantic locator, `--all`, and the
sibling `count` command all handle a miss correctly — so this is an inconsistency inside
one subcommand, not a missing capability.

## Where this came from

This defect was **named by a maintainer**, not by us. Closing
[#212](https://github.com/VibiumDev/vibium/issues/212) on 2026-08-02 (a report whose own
premise did not hold), `hugs` wrote:

> There is one real defect in the neighbourhood, though it is not what was reported:
> `browserFind` writes a @ref without checking that the lookup returned anything
> (`handlers.go:1020-1027`), so a miss can still mint a ref. Worth a 3-line guard.

No issue was opened for it, and no commit since touches it (checked across all 198
commits from 2026-06-01 to 2026-08-07). This write-up supplies the repro, the blast
radius, and the two symptoms not mentioned in that sentence.

## The two symptoms beyond the original description

1. **A raw Go `<nil>` reaches user-facing output.** Not a formatting nit — it is the
   only signal that anything went wrong, and it appears *inside* an otherwise
   well-formed ref line.
2. **`--json` reports `"ok":true`.** Any machine consumer — a script, an agent, a CI
   step — reads a failed lookup as a success. This is the more serious of the two,
   because the plain-text `<nil>` is at least visible to a human.

## The correct behaviour already exists, in the same subcommand

Measured on v26.5.31, `https://example.com`, all selectors guaranteed to match nothing:

| command | output | exit | correct? |
|---|---|---|---|
| `find "#nope-zzz"` | `@e1 <nil>` | 0 | ✗ **mints a ref** |
| `find "#nope-zzz" --json` | `{"ok":true,"result":"@e1 <nil>"}` | 0 | ✗ **reports success** |
| `find "#nope-zzz" --all` | `No elements found` | 0 | ✓ |
| `find text "NoSuchTextZZZ"` | `Error: element not found: text=NoSuchTextZZZ (timeout 30s)` | 1 | ✓ |
| `find label "NoSuchLabelZZZ"` | `Error: element not found: label=NoSuchLabelZZZ (timeout 30s)` | 1 | ✓ |
| `find placeholder "NoSuchPlaceholderZZZ"` | `Error: element not found: placeholder=… (timeout 30s)` | 1 | ✓ |
| `count "#nope-zzz"` | `0` | 0 | ✓ |

Control, same session — a selector that *does* match:

```sh
vibium find "h1"
# → @e1 [h1] "Example Domain"
# exit 0
```

`find testid`, `find xpath` and `find role` were each observed still waiting at 8s,
consistent with the same 30s auto-wait path as the other semantic locators; their final
output was not captured, so they are **not** claimed as verified here.

## The minted ref overwrites a previously valid one

The bogus ref is not appended — it takes the `@e1` slot. A sequence that finds a real
element and then misses silently loses the good ref:

```sh
vibium find "h1"          # → @e1 [h1] "Example Domain"
vibium find "#nope-zzz"   # → @e1 <nil>            ← @e1 now points at nothing
vibium click "@e1"        # → Error: ... element not found
```

## Impact

The exit-0 miss defeats the standard defensive pattern. A script that checks `find`'s
exit code before using the ref passes the check and fails at the *next* command, with an
error naming `click` rather than the selector that was actually wrong:

```sh
if vibium find "$SEL"; then
  vibium click "@e1"      # ← fails here, pointing at the wrong step
fi
```

For agent use the `--json` case is worse: `{"ok":true}` is exactly the field an agent
keys on to decide the step succeeded.

Severity **Medium**, priority **P2** — not data-destructive and there is a workaround,
but it converts a clear failure into a misattributed one, and the `--json` path is
silently wrong to machine consumers.

## Workaround

Use `count` as a guard, or `find --all`, both of which report a miss correctly:

```sh
[ "$(vibium count "$SEL")" -gt 0 ] && vibium click "$SEL"
```

## Suggested fix

The guard `hugs` described: in `browserFind` (`handlers.go:1020-1027`), check that the
lookup returned an element before writing the ref, and return the same
`element not found: <locator>` error the semantic locators already produce. Making the
CSS path match its siblings would fix the plain output, the `--json` `ok` field, and the
exit code together.

Not proposed here: changing `--all`'s exit code, or the semantic locators' 30s wait —
both are out of scope and behave sensibly today.

## Scope

- **Verified:** macOS darwin 25.5.0, vibium v26.5.31 (installed = npm `latest`,
  published 2026-06-01), two sites — `example.com` and `coffee-cart.app`, identical
  behaviour on both.
- **Not verified:** Linux, Windows. Nothing about the path looks platform-specific, but
  it has not been checked.
- **Not verified against `main`.** v26.5.31 predates the large August fix run; whether
  anything there incidentally touched this is untested and untestable until the next npm
  publish. Happy to retest on `main` or after publish.
