# screenshot -o — output path silently discarded; CLI inherits the MCP sandbox

**vibium v26.5.31 · macOS darwin 25.5.0 · verified against repo source**
**Filed as:** _not yet filed_
**Affects:** `vibium screenshot` — `pdf`, `storage` and `record stop` are unaffected

## Summary

`vibium screenshot -o <path>` keeps only the **basename** and writes to
`~/Pictures/Vibium/<basename>` regardless of the directory given. `--help` documents the
flag as `-o, --output string   Output file path`.

This is not an oversight. The CLI dispatches to the same daemon handler the MCP server
uses, and that handler deliberately strips the directory as a path-traversal guard. The
guard is correct for MCP — an agent should not write to arbitrary paths — but the CLI is
a user directing their own shell, and there it silently discards intent. The MCP surface
is *also* the only one with a way to configure the destination.

## Root cause

The CLI command forwards to the MCP-facing handler:

```go
// clicker/cmd/clicker/screenshot.go
result, err := daemonCall("browser_screenshot", screenshotArgs)
```

which flattens the path:

```go
// clicker/internal/agent/handlers.go
// Use only the basename to prevent path traversal
safeName := filepath.Base(filename)
fullPath := filepath.Join(h.screenshotDir, safeName)
```

`h.screenshotDir` is fixed at daemon start with no override, and unlike its sibling in
the same file it consults no environment variable:

```go
// clicker/cmd/clicker/daemon_cmd.go
screenshotDir := ""
defaultDir, err := paths.GetScreenshotDir()
if err == nil { screenshotDir = defaultDir }
```

```go
// clicker/internal/paths/paths.go
// GetScreenshotDir returns the platform-specific default directory for screenshots.
// macOS: ~/Pictures/Vibium/   Linux: ~/Pictures/Vibium/   Windows: %USERPROFILE%\Pictures\Vibium\
func GetScreenshotDir() (string, error) {
    home, err := os.UserHomeDir()          // no env var consulted

// ...while the sibling helper in the SAME file is configurable:
func GetCacheDir() (string, error) {
    if cacheDir := os.Getenv("VIBIUM_CACHE_DIR"); cacheDir != "" { return cacheDir, nil }
```

There is no `VIBIUM_SCREENSHOT_DIR` equivalent.

**The guard works against a malicious argument** — `-o "../../../../tmp/trav.png"` stays
in `~/Pictures/Vibium/trav.png`, and a symlinked *path component* is stripped before
resolution too (`-o "linkdir/x.png"` → `~/Pictures/Vibium/x.png`).

**But it is not a complete confinement boundary.** A symlink already sitting at the
destination filename is followed, because `filepath.Base` passes it trivially and the
write resolves it:

```sh
ln -s /tmp/escape/out.png ~/Pictures/Vibium/sneaky.png
vibium screenshot -o sneaky.png
# → "Screenshot saved to ~/Pictures/Vibium/sneaky.png"
#   49,720 bytes actually written to /tmp/escape/out.png — outside the sandbox
```

Stated fairly: this is a defence-in-depth gap, not a remotely exploitable one. Planting
the symlink needs prior write access to `~/Pictures/Vibium/`, which `browser_screenshot`
alone does not grant — it writes PNG bytes, it cannot create links. So the guard still
does its main job of neutralising a hostile `filename`.

It does mean the guard is not airtight, which matters for the argument: it is not strong
enough to justify the usability cost it imposes on the CLI, where there is no adversary
at all. If confinement is the goal, `O_NOFOLLOW` or resolving the final path and checking
containment would close the symlink case; neither requires flattening the CLI's `-o`.

The guard appears **long-standing rather than a regression** — no commit in the recent
history of `handlers.go` introduces it, and the file predates the March 2026
`mcp → agent` package rename.

## The capability to do the right thing is already present

Two behaviours found by pointing `vibium mcp --screenshot-dir` at hostile destinations
show the code already handles everything the fix needs — it just never applies it to the
user's `-o`.

**Directory trees are created on demand.** Pointing at a path several levels deep that
does not exist:

```
--screenshot-dir /tmp/b35-fresh/nested/deep
browser_screenshot { filename: "probe.png" }
→ "Screenshot saved to /tmp/b35-fresh/nested/deep/probe.png"   (tree created)
```

`mcp_cmd.go` carries an explicit `// Create directory if it doesn't exist`. So
"we would have to create the directory" is not an objection to honouring `-o`.

**Path failures are reported clearly — when they are allowed to surface.** A read-only
destination:

```
→ "failed to save screenshot: open /tmp/b35-ro/probe.png: permission denied"
```

and an over-long name:

```
→ "failed to save screenshot: open .../<296 chars>.png: file name too long"
```

Both are exactly the right error shape. The contrast is the point: this code reports
filesystem problems accurately, and silently swallows only the one case where the user
told it where to write.

**A no-disk mode already exists.** `--screenshot-dir ""` disables file saving entirely:

```
→ "screenshot file saving is disabled (use --screenshot-dir to enable)"
```

Three destination modes are therefore already modelled — default, configured, disabled —
and none of them is reachable from the CLI.

## The asymmetry

| Surface | Traversal guard | Configurable destination |
|---|---|---|
| MCP (`vibium mcp`) | needed | **yes** — `--screenshot-dir ./shots`, `--screenshot-dir ""` to disable |
| CLI (`vibium screenshot`) | not needed | **no** — `-o` is discarded; `vibium daemon start --screenshot-dir` → `unknown flag` |

The MCP default is documented (`docs/tutorials/getting-started-mcp.md`:
*"Screenshots are saved to `~/Pictures/Vibium/`"*). There is no equivalent CLI
documentation, and `screenshot --help` describes `-o` as an output **path**.

Verified the MCP override works — driving the server over stdio with
`--screenshot-dir /tmp/mcpshots` and asking for a path elsewhere:

```
browser_screenshot { filename: "/some/other/dir/mcp-test.png" }
→ "Screenshot saved to /tmp/mcpshots/mcp-test.png"
```

The basename guard applies there too, correctly — but the base directory is the caller's
choice. On the CLI it is neither honoured nor configurable.

## Repro

```sh
cd /tmp
vibium go https://example.com
vibium screenshot -o /tmp/check.png
ls /tmp/check.png
```

```
Screenshot saved to /Users/<you>/Pictures/Vibium/check.png
ls: /tmp/check.png: No such file or directory
```

Every path form collapses identically:

| `-o` argument | Written to |
|---|---|
| `shot.png` | `~/Pictures/Vibium/shot.png` |
| `./shot.png` | `~/Pictures/Vibium/shot.png` |
| `~/shot.png` | `~/Pictures/Vibium/shot.png` |
| `/abs/path/shot.png` | `~/Pictures/Vibium/shot.png` |
| `sub/shot.png` | `~/Pictures/Vibium/shot.png` — `sub/` dropped, not created |
| `/abs/nonexistent/shot.png` | `~/Pictures/Vibium/shot.png` — no error |
| `../../../../tmp/shot.png` | `~/Pictures/Vibium/shot.png` — guard working as designed |

`--full-page` and `--annotate` behave the same. Default with no `-o` is
`~/Pictures/Vibium/screenshot.png`, consistent with `--help`.

## Sibling commands are unaffected

They do not route through this handler:

| Command | Honours `-o` |
|---|---|
| `vibium screenshot -o` | **no** |
| `vibium pdf -o` | yes |
| `vibium storage -o` | yes |
| `vibium record stop -o` | yes |

Verified in one run against the same absolute target directory.

## Secondary defects in the same path

Found while hardening; all follow from flattening to a single shared directory.

**Silent success.** No warning that the path was discarded, and the machine-readable
output reports plain success at the redirected location:

```sh
vibium screenshot --json -o /some/dir/g.png
# {"ok":true,"result":"Screenshot saved to /Users/<you>/Pictures/Vibium/g.png"}
```

A script that writes and then reads back from the path it supplied fails at the read,
one step from the cause.

**Collisions overwrite silently.** Because only the basename survives, two runs writing
`report.png` to *different* directories become the same file. Simulating two CI shards:

```
shard-a  vibium screenshot -o /tmp/shard-a/report.png   → 49,720 bytes  sha f487928dd6e7
shard-b  vibium screenshot -o /tmp/shard-b/report.png   → 84,845 bytes  sha 06194b81da96

/tmp/shard-a/  0 files
/tmp/shard-b/  0 files
~/Pictures/Vibium/report.png  ← one file; shard-a's artefact is unrecoverable
```

Sharding a matrix build by output directory — the standard way to keep parallel jobs from
colliding — provides no isolation here, and the loss is silent.

Two *simultaneous* writes to the same basename were also tested: the result is
last-writer-wins with a valid PNG, not a corrupt one. So the failure mode is losing an
artefact, never a truncated file — which bounds the severity but does not remove it.

**A trailing-slash directory produces an extensionless file.**
`filepath.Base("/tmp/")` is `"tmp"`:

```sh
vibium screenshot -o /tmp/
# Screenshot saved to ~/Pictures/Vibium/tmp        ← a PNG named "tmp"
```

**Exit code is 0** despite the path being discarded, so `set -e` scripts continue past it
and fail later at the read.

**Every invocation form behaves identically** — `--full-page`, `--annotate`, and the
navigate-then-capture form `vibium screenshot <url> -o <path>`.

**`-o ""` is a silent no-op** — no output on stdout or stderr, exit code 0, nothing
written.

**Windows-style paths are not split on Unix.** `filepath.Base` only splits on `/` here, so
the same argument produces different filenames per platform:

```sh
vibium screenshot -o 'C:\temp\win.png'
# macOS  → a file literally named  C:\temp\win.png
# Windows → would split to          win.png
```

A cross-platform script gets different results from identical input.

Spaces, unicode, leading dashes and 124-character basenames all pass through unchanged.

**The extension is ignored.** Output is always PNG regardless of what is asked for:

```sh
vibium screenshot -o shot.jpg
file ~/Pictures/Vibium/shot.jpg
# PNG image data, 2400 x 2364        ← PNG content, .jpg name
```

## Impact

Any scripted or CI use that collects screenshots into a working directory, an artefact
folder or a per-run temp directory silently gets nothing there, and parallel runs clobber
one another in the single shared directory. Every capture needs a follow-up copy, and the
source filename must be derived by hand.

Because no invocation can direct output anywhere, that one directory becomes a shared
dumping ground across every project a user ever runs. On this machine it currently holds
**702 PNGs totalling 367 MB across 179 distinct basename prefixes**, accumulated from
unrelated pieces of work with no way to separate them at capture time — and any two of
those that shared a basename overwrote each other silently.

## Workaround

```sh
out=/my/target/shot.png
vibium screenshot -o "$out" >/dev/null
cp ~/Pictures/Vibium/"$(basename "$out")" "$out"
```

For pixel-exact work, avoid the command entirely — `toDataURL` returns the canvas or page
bitmap at native resolution without touching the filesystem, and is not device-pixel
scaled the way screenshots are.

## Suggested fix

Naively honouring `-o` would reintroduce the traversal risk on MCP, so the fix should be
surface-aware:

1. **Keep the guard for the agent surface.** `browser_screenshot` invoked over MCP should
   continue to confine writes to the configured `screenshotDir`.
2. **Honour the path on the CLI.** The user's own shell is not an untrusted caller.
   Resolve `-o` (expanding `~`, taking relative paths against cwd), create the directory
   or fail loudly, and write there. This likely means passing a trusted/local flag through
   `daemonCall`, or resolving the path CLI-side before dispatch.

   **The pattern already exists in the codebase** — `internal/api/recording.go`:

   ```go
   // WriteRecordToFile writes recording zip data to a file, creating directories as needed.
   func WriteRecordToFile(data []byte, path string) error {
       dir := filepath.Dir(path)
       if err := os.MkdirAll(dir, 0o755); err != nil {
           return fmt.Errorf("failed to create recording dir: %w", err)
       }
       return os.WriteFile(path, data, 0o644)
   }
   ```

   That is precisely why `record stop -o` honours its path, and
   `internal/api/handlers_download.go` does the same for downloads. Reusing it for the
   trusted CLI path would make the four commands consistent.

   Note the screenshot write itself is currently bare — `os.WriteFile(fullPath, pngData,
   0644)` with no `MkdirAll` — because the directory is created earlier, when
   `--screenshot-dir` is processed. Extending that same creation step to a trusted `-o`
   is a small change, not a new subsystem.
3. **Failing that, at minimum warn.** If the directory is going to be discarded, say so on
   stderr and report `ok:false` — or reflect the true destination — rather than reporting
   success at a path the caller did not choose.
4. **Consider `--screenshot-dir` on `vibium daemon start`,** mirroring `vibium mcp`. Not a
   substitute for honouring `-o`, but it would give CLI users the escape hatch MCP users
   already have.

Independently worth addressing: silent overwrite on basename collision, the
trailing-slash case producing an extensionless file, and the ignored extension.

## Scope

Verified on macOS darwin 25.5.0, vibium v26.5.31. **Not macOS-specific** —
`GetScreenshotDir()` applies the same `Pictures/Vibium` convention on Linux and Windows,
so the behaviour should reproduce there, though it has not been run on those platforms.

No existing upstream issue matches (`screenshot`, `output path`, `Pictures` all searched).
