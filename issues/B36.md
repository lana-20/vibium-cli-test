# `page.eval` discards script exceptions — all three client libraries silently return null

**vibium v26.5.31 · macOS darwin 25.5.0 · verified against repo source**
**Filed as:** _not yet filed_
**Affects:** the Python, JavaScript and Java client libraries. CLI and MCP take a
different path and are **not** affected by this (they have their own, separate defect —
see [#221](https://github.com/VibiumDev/vibium/issues/221)).

## Summary

When an evaluated expression throws, `vibium:page.eval` reports **success** with a null
value. Every client library therefore returns `None` / `null` and raises nothing, making a
broken script indistinguishable from one that legitimately returned nothing.

This is distinct from #221. That issue is about the CLI/MCP path producing an *empty error
message*; there, failure is at least signalled. Here failure is not signalled at all, and
the fix for #221 does not touch this code.

## Reproduce

Python:

```python
from vibium import browser
b = browser.start(headless=True)
p = b.new_page(); p.go("https://example.com")

p.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()")   # → None, no exception
p.evaluate("null.foo")                                              # → None, no exception
p.evaluate("totallyUndefinedThing.bar")                             # → None, no exception
p.evaluate("const = = 5")                                           # → None, no exception
p.evaluate("1 + 1")                                                 # → 2      (control)
```

JavaScript:

```js
await page.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()")  // → null, no throw
await page.evaluate("null.foo")                                             // → null, no throw
await page.evaluate("1 + 1")                                                // → 2   (control)
```

Java:

```java
p.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()");  // → null, no exception
p.evaluate("null.foo");                                             // → null, no exception
p.evaluate("null");                                                 // → null  (indistinguishable)
p.evaluate("1 + 1");                                                // → 2     (control)
```

**Expected:** an exception, carrying the JavaScript error message.
**Actual:** a normal return of null, identical to `evaluate("null")`.

## Root cause

`Router.handlePageEval` in `clicker/internal/api/handlers_state.go`:

```go
resp, err := r.sendInternalCommand(session, "script.evaluate", map[string]interface{}{
    "expression": expression, "target": …, "awaitPromise": true, "resultOwnership": "none",
})
if err != nil { r.sendError(session, cmd.ID, err); return }

if bidiErr := checkBidiError(resp); bidiErr != nil { r.sendError(session, cmd.ID, bidiErr); return }

value, err := deserializeScriptResult(resp)
if err != nil { r.sendError(session, cmd.ID, fmt.Errorf("eval failed: %w", err)); return }

r.sendSuccess(session, cmd.ID, map[string]interface{}{"value": value})
```

There is **no `Type == "exception"` check anywhere in this path.**

A thrown script is not a BiDi protocol error — WebDriver BiDi returns a successful
`script.evaluate` response whose *result* carries `type: "exception"` with
`exceptionDetails`. So:

1. `sendInternalCommand` succeeds — no transport error.
2. `checkBidiError(resp)` passes — there is no protocol-level error.
3. `deserializeScriptResult(resp)` yields nil for an exception result.
4. `sendSuccess` is called with `{"value": nil}`.

The client receives a well-formed success response. Compare the sibling path used by the
CLI and MCP, `bidi.Client.Evaluate()` / `CallFunction()` in `clicker/internal/bidi/script.go`,
which *does* check:

```go
if callResult.Type == "exception" {
    return nil, fmt.Errorf("script exception: %s", string(callResult.Result))
}
```

That check is the one #221 is about — correct in shape, wrong in the field it reads.
`handlePageEval` has no equivalent at all.

## Why the clients cannot compensate

Their error handling is correct; they are never given an error. The Python client, for
example, raises properly on any error response:

```python
# vibium/client.py
if response.get("type") == "error":
    error_code = response.get("error", "unknown")
    error_message = response.get("message", "Unknown error")
    ...
    raise BiDiError(error_code, error_message)
return response.get("result")
```

Confirmed working — an unrelated failure surfaces normally:

```python
p.go("not-a-url://x")   # → BiDiError: error: unknown error: net::ERR_ABORTED
```

So the clients raise when told to. They are simply never told.

## Additional note on the JavaScript client

Independently of the above, the JS dispatcher guards on both the type **and** a truthy
error field:

```js
// clients/javascript/dist/index.mjs:312
if (response.type === "error" && response.error) {
  pending.reject(new Error(`${response.error}: ${response.message}`));
} else {
  pending.resolve(response.result);
}
```

If `handlePageEval` is fixed to send an error whose `error` field is empty — which is what
`bidi/script.go` currently produces before #221 lands — this client would still resolve
instead of rejecting. Worth dropping the `&& response.error` regardless, so an empty error
string cannot silently become a success.

## Impact

Any script that throws looks like a script that returned nothing. Nothing in the client
API distinguishes them, so failures propagate as null values into user code and surface
later, somewhere else, as a `NoneType`/`undefined` error with no connection to the cause.

It is particularly corrosive in tests. **Any assertion expecting a null result passes
whether the value was genuinely absent or the script threw.** We found and fixed two such
assertions in our own suites once this behaviour was understood — one in a JavaScript suite
asserting `expect(val).toBeNull()` after a `clearStorage`, one in a Java suite asserting
`assertEquals(null, page.evaluate("null"))`. Both had been passing for the wrong reason and
would not have caught a regression that broke `evaluate` outright.

## Suggested fix

Add the exception check to `handlePageEval` before `sendSuccess`, mirroring
`bidi.Client.Evaluate()`, and send an error carrying `exceptionDetails.text`. Applying
#221's field correction at the same time means both paths report the real message rather
than an empty one.

Worth auditing the other handlers in `handlers_state.go` that call `script.evaluate` or
`script.callFunction` through `sendInternalCommand`, in case the same check is missing
elsewhere.

## Scope

Verified on macOS darwin 25.5.0, vibium v26.5.31, across all three client libraries with a
`1 + 1` → `2` control in each. Not tested on other platforms; the code path is
platform-independent so it should reproduce anywhere.

No existing upstream issue matches — searched `script exception`, `evaluate null`,
`page.eval`.

## Test entry

```python
from vibium import browser
b = browser.start(headless=True)
p = b.new_page(); p.go("https://example.com")
try:
    p.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()")
    print("FAIL — no exception raised")
except Exception as e:
    print("PASS —", e)
```

PASS if: an exception is raised carrying `CUSTOM_MESSAGE_HERE`
FAIL if: the call returns `None` and nothing is raised

Control, which must keep working: `p.evaluate("1 + 1")` → `2`, and
`p.evaluate("null")` → `None` without raising.
