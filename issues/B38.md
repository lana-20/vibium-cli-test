# B38 — BiDi error detail is discarded and the error code is printed twice

**vibium v26.5.31 and `main` @ `59e4b4b` · macOS 26.5.2 (25F84) x86_64**
**Filed as:** _not yet filed_ — draft awaiting review. No upstream issue covers this
(searched: "BiDi error duplicate message", "session not created"; only #240/#158/#159, all
closed and all about `--connect`, not the error text).

> **File as a DEFECT, not an enhancement.** The code *tries* to surface the detail and
> fails: `ErrorData` declares a `Message` field, the format string joins two values with
> `" - "`, and `api/helpers.go:38` `checkBidiError` already parses the flat shape
> correctly. Existing behaviour not working as written, on one of two paths that disagree.

> **Severity Medium · Priority P2.** No operation produces a wrong result — only the
> explanation is destroyed. Rated above its severity because there is **no workaround**
> (`-v`/`--verbose` do not help), it fires on everyday commands (`vibium go` with a typo'd
> URL), ~19 `SendCommand` call sites funnel through the one formatter, and an agent reading
> `invalid argument - invalid argument` has no signal to self-correct. Upstream has fixed
> five issues of this exact class (#221, #111, #161, #213, #64), so it is in-scope for them.

---

## Description

When a WebDriver BiDi command fails, Vibium prints the error **code twice** and drops the
`message` field entirely, so the error text never says what actually went wrong:

```
$ vibium --headless go "not-a-real-url"
Error: failed to navigate: BiDi error: invalid argument - invalid argument
```

Chrome sends a perfectly good explanation in the response; Vibium discards it while parsing.

This affects every error surfaced through the BiDi client — `browsingContext.navigate`,
`captureScreenshot`, `script.evaluate` / `script.callFunction` (so all element interactions),
`input.performActions` (all mouse/keyboard), `storage.getCookies` / `setCookie`, `getTree`.

There is **no workaround**: `-v` / `--verbose` do not surface the detail either, because the
field is dropped at parse time rather than merely not printed.

## Steps to Reproduce

### Repro A — real Chrome, no setup (3 one-liners)

Any malformed argument to a command that reaches the browser:

```bash
vibium --headless go "not-a-real-url"
# Error: failed to navigate: BiDi error: invalid argument - invalid argument

vibium --headless go "http://"
# Error: failed to navigate: BiDi error: invalid argument - invalid argument
```

In both cases the error code `invalid argument` is printed twice. Captured directly off the
BiDi socket, Chrome's replies to those two navigations were:

```json
{"type":"error","id":99,"error":"invalid argument","message":"Invalid URL: not-a-real-url"}
{"type":"error","id":99,"error":"invalid argument","message":"Invalid URL: http://"}
```

so `Invalid URL: not-a-real-url` — the part that tells you what was wrong — is what gets
dropped.

### Repro B — isolated, shows exactly what is thrown away (no browser needed)

A fake BiDi endpoint that replies to `session.new` with a normal, spec-shaped error. Save as
`fake_bidi.py` (requires `pip install websockets`):

```python
import asyncio, json, sys, websockets

PORT = int(sys.argv[1])
DETAIL = "invalid argument: capability 'foo' is not supported by this endpoint"

async def handler(ws):
    async for raw in ws:
        msg = json.loads(raw)
        mid, method = msg.get("id"), msg.get("method")
        if method == "session.status":
            await ws.send(json.dumps({"id": mid, "type": "success",
                                      "result": {"ready": True, "message": ""}}))
        elif method == "session.new":
            await ws.send(json.dumps({"id": mid, "type": "error",
                                      "error": "invalid argument", "message": DETAIL}))
        else:
            await ws.send(json.dumps({"id": mid, "type": "success", "result": {}}))

async def main():
    async with websockets.serve(handler, "127.0.0.1", PORT):
        print("listening", flush=True)
        await asyncio.Future()

asyncio.run(main())
```

Run it, then point Vibium at it:

```bash
python3 fake_bidi.py 9700 &
sleep 1
{ sleep 2; } | vibium pipe --connect ws://127.0.0.1:9700
```

Output:

```
[router] Connecting to remote browser for client 1: ws://127.0.0.1:9700
[router] Failed to connect to remote browser for client 1: BiDi error: invalid argument - invalid argument
```

The endpoint sent `"message": "invalid argument: capability 'foo' is not supported by this
endpoint"`. It appears nowhere in the output, with or without `-v`.

### Repro C — confirms the parser is written for a shape BiDi never sends

Change only the error's **shape** in the script above, from the flat form the spec uses to a
nested one:

```python
# flat (what WebDriver BiDi actually sends)
{"id": mid, "type": "error", "error": "invalid argument", "message": DETAIL}

# nested (what the parser expects)
{"id": mid, "type": "error", "error": {"error": "invalid argument", "message": DETAIL}}
```

Same binary, same detail string:

```
flat    -> BiDi error: invalid argument - invalid argument
nested  -> BiDi error: invalid argument - invalid argument: capability 'foo' is not supported by this endpoint
```

The detail is only reported for a shape no real endpoint produces.

## Expected Behavior

```
Error: failed to navigate: BiDi error: invalid argument - Invalid URL: not-a-real-url
```

The code once, then the detail the browser sent.

## Actual Behavior

```
Error: failed to navigate: BiDi error: invalid argument - invalid argument
```

The code twice, no detail.

## Root Cause

A BiDi error response carries the code in `error` and the detail in a **sibling** `message`
field — not nested inside `error`:

```json
{"type":"error","id":1,"error":"invalid argument","message":"invalid argument: ..."}
```

Two things go wrong in `clicker/internal/bidi/protocol.go`:

**1. `Message` has no field for the sibling `message`** (lines 43-52), so `encoding/json`
discards the detail while parsing the frame. Nothing downstream can print what was never
deserialized:

```go
type Message struct {
	ID     *int64          `json:"id,omitempty"`
	Result json.RawMessage `json:"result,omitempty"`
	Error  json.RawMessage `json:"error,omitempty"`
	Method string          `json:"method,omitempty"`
	Params json.RawMessage `json:"params,omitempty"`
	// no field for the top-level `message`
}
```

**2. `GetError` (lines 70-86) targets a shape BiDi never sends.** It first tries to unmarshal
`m.Error` into `ErrorData{Error, Message}`, which only succeeds if the wire had
`"error": {"error": ..., "message": ...}`. Against any spec-compliant endpoint `m.Error` is the
bare string `"invalid argument"`, so that unmarshal always fails and control reaches the
fallback — which **fabricates** the detail by copying the code:

```go
var errData ErrorData
if err := json.Unmarshal(m.Error, &errData); err != nil {   // always fails in practice
	var errStr string
	if err := json.Unmarshal(m.Error, &errStr); err != nil {
		return nil, err
	}
	return &ErrorData{Error: errStr, Message: errStr}, nil   // Message := the code
}
```

By the time `session.go:244` formats the message, both arguments hold the same string:

```go
return nil, fmt.Errorf("BiDi error: %s - %s", errData.Error, errData.Message)
```

The doubling is the visible symptom; the detail was destroyed one layer earlier. **This is a
parse bug, not a formatting bug** — changing the format string cannot help, because the data is
already gone before it is reached.

## Proposed Fix

Capture the sibling `message` on `Message`, and use it in `GetError`'s string branch instead of
copying `errStr`. The format string needs no change.

```diff
--- a/clicker/internal/bidi/protocol.go
+++ b/clicker/internal/bidi/protocol.go
@@ type Message struct {
 	// Event fields
 	Method string          `json:"method,omitempty"`
 	Params json.RawMessage `json:"params,omitempty"`
+
+	// ErrMessage carries the error detail. BiDi sends `message` as a sibling
+	// of `error`, not nested inside it, so it must be captured here.
+	ErrMessage string `json:"message,omitempty"`
 }
@@ func (m *Message) GetError() (*ErrorData, error) {
 		var errStr string
 		if err := json.Unmarshal(m.Error, &errStr); err != nil {
 			return nil, err
 		}
-		return &ErrorData{Error: errStr, Message: errStr}, nil
+		// `error` is a bare code string, so the detail is the sibling
+		// `message`. Falling back to the code would report it twice.
+		detail := m.ErrMessage
+		if detail == "" {
+			detail = errStr
+		}
+		return &ErrorData{Error: errStr, Message: detail}, nil
 	}
 	return &errData, nil
 }
```

Two notes that may be useful:

- **The correct parse already exists in-tree.** `api/helpers.go:38` `checkBidiError` declares
  `Type` / `Error` / `Message` as flat siblings and formats `"%s: %s"`. The two error paths
  currently disagree, so which text a user sees depends on which path surfaced the error.
- **There is no test coverage** for `GetError`, `ErrorData`, or BiDi error text anywhere in the
  tree — likely how this survived the reader-goroutine refactor that moved the formatter into
  `responseOrError`. A regression test is suggested below.

### Suggested regression test

`clicker/internal/bidi/protocol_error_test.go`:

```go
package bidi

import "testing"

// A WebDriver BiDi error response carries the error code in `error` and the
// human-readable detail in a sibling `message` field:
//
//	{"type":"error","id":1,"error":"invalid argument","message":"invalid argument: ..."}
//
// GetError must report the detail, not a second copy of the code.
func TestGetErrorKeepsSiblingMessage(t *testing.T) {
	raw := `{"type":"error","id":1,"error":"invalid argument",` +
		`"message":"Invalid URL: not-a-real-url"}`

	msg, err := UnmarshalMessage([]byte(raw))
	if err != nil {
		t.Fatalf("UnmarshalMessage: %v", err)
	}
	if !msg.IsError() {
		t.Fatal("expected an error message")
	}

	errData, err := msg.GetError()
	if err != nil {
		t.Fatalf("GetError: %v", err)
	}
	if errData.Error != "invalid argument" {
		t.Errorf("code = %q, want %q", errData.Error, "invalid argument")
	}
	want := "Invalid URL: not-a-real-url"
	if errData.Message != want {
		t.Errorf("detail = %q, want %q", errData.Message, want)
	}
	if errData.Message == errData.Error {
		t.Error("detail is a duplicate of the code; sibling `message` was dropped")
	}
}

// The nested shape must keep working.
func TestGetErrorNestedObjectStillParses(t *testing.T) {
	raw := `{"type":"error","id":1,"error":{"error":"invalid argument","message":"detail here"}}`
	msg, err := UnmarshalMessage([]byte(raw))
	if err != nil {
		t.Fatalf("UnmarshalMessage: %v", err)
	}
	errData, err := msg.GetError()
	if err != nil {
		t.Fatalf("GetError: %v", err)
	}
	if errData.Message != "detail here" {
		t.Errorf("detail = %q, want %q", errData.Message, "detail here")
	}
}
```

On current `main` the first test fails and the second passes:

```
=== RUN   TestGetErrorKeepsSiblingMessage
    protocol_error_test.go:32: detail = "invalid argument", want "Invalid URL: not-a-real-url"
    protocol_error_test.go:35: detail is a duplicate of the code; sibling `message` was dropped
--- FAIL: TestGetErrorKeepsSiblingMessage (0.00s)
=== RUN   TestGetErrorNestedObjectStillParses
--- PASS: TestGetErrorNestedObjectStillParses (0.00s)
```

With the fix above applied, both pass.

  string was byte-identical across all 10 regardless of the nonce.

  cause.

  still parsing and normal attach to a live chromedriver session unaffected.
