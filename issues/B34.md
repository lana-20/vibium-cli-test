## Comment draft for #221

Confirming this on v26.5.31 (macOS darwin 25.5.0) and adding scope data — the blast
radius is wider than `eval` alone.

**Every exception class, not just `SecurityError`/`ReferenceError`.** All return the
identical empty message:

| Expression | Class |
|---|---|
| `const zz = 1` twice in one document | SyntaxError (redeclaration) |
| `const = = 5` | SyntaxError (malformed) |
| `totallyUndefinedThing.foo` | ReferenceError |
| `null.foo` | TypeError |
| `(() => { throw new Error("CUSTOM_MESSAGE_HERE") })()` | Error, custom message |
| `(() => { throw "PLAIN_STRING_THROWN" })()` | thrown primitive |

A custom message passed to `new Error()` is discarded too, so this is not only about
browser-generated errors.

**The detail is unrecoverable through every documented flag:**

```
vibium eval '<throws>'            → Error: failed to evaluate: script exception:
vibium eval --json '<throws>'     → {"ok":false,"error":"failed to evaluate: script exception: "}
vibium eval -v '<throws>'         → no additional detail
vibium eval --stdin <heredoc>     → Error: failed to evaluate: script exception:
exit code                         → 1 (correct)
```

The `--json` form corroborates the root cause in this issue: note the **trailing space**
after `exception:`. The format string interpolates a value that is empty, exactly as
`string(evalResult.Result)` would be for an exception response.

**The client libraries are worse than the CLI — they swallow the exception entirely.**
On the Python and JavaScript clients a throwing expression does not raise at all; it
returns `None` / `null`, which is indistinguishable from a script that legitimately
returned nothing:

```python
# vibium Python client, v26.5.31
p.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()")   # → None, no exception
p.evaluate("null.foo")                                              # → None, no exception
p.evaluate("totallyUndefinedThing.bar")                             # → None, no exception
p.evaluate("const = = 5")                                           # → None, no exception
p.evaluate("1 + 1")                                                 # → 2      (control)
```

```js
// vibium JavaScript client, v26.5.31
await page.evaluate("(() => { throw new Error('CUSTOM_MESSAGE_HERE') })()")  // → null, no throw
await page.evaluate("null.foo")                                             // → null, no throw
await page.evaluate("1 + 1")                                                // → 2   (control)
```

So the severity is not uniform across surfaces:

| Surface | On a throwing expression |
|---|---|
| CLI | exit 1, `script exception:` — empty, but failure *is* signalled |
| MCP | same as CLI |
| Python client | **returns `None`, no exception raised** |
| JavaScript client | **returns `null`, no throw** |
| Java client | not tested |

The CLI at least tells you something went wrong. The clients do not, which makes a broken
script silently indistinguishable from a working one that returns null — and any test
asserting a null/None result will pass while the underlying JavaScript is throwing.

**Confirmed on the MCP surface as well**, so a CLI-only fix would be partial:

```
browser_evaluate { expression: "(() => { throw new Error(\"CUSTOM_MESSAGE_HERE\") })()" }
→ failed to evaluate: script exception:
```

Byte-identical to the CLI, from a separate browser instance — consistent with both
routing through `bidi.Client.Evaluate()`.

**Control — the exception data is reachable, it is only lost on the error path.** The
same error caught inside the expression returns in full:

```sh
vibium eval "(() => { try { null.foo } catch (e) { return e.constructor.name + ': ' + e.message } })()"
# → TypeError: Cannot read properties of null (reading 'foo')

vibium eval 'null.foo'
# → Error: failed to evaluate: script exception:
```

Useful as a workaround in the meantime: wrap the payload in `try/catch` and return
`e.message` as a value.

**Page-independent** — same result on example.com, testtrack.org/canvas-demo and
saucedemo.com.

**Both comparable tools return the message.** Identical expression, identical page,
measured 2026-07-28:

```
Playwright 1.62   page.evaluate: Error: CUSTOM_MESSAGE_HERE
Selenium 4.44     javascript error: CUSTOM_MESSAGE_HERE
vibium 26.5.31    failed to evaluate: script exception:      ← nothing after the colon
```

Same for a `TypeError`: both return *"Cannot read properties of null (reading 'foo')"*,
vibium returns the empty string. This is not a hard problem that peers have also failed
to solve — it is a field being read from the wrong place, and the fix restores parity
with the rest of the ecosystem.

**One more call site worth folding into the same fix.**
[#156](https://github.com/VibiumDev/vibium/issues/156) reports
`failed to annotate: script exception:` — the same truncated suffix from
`browser_screenshot { annotate: true }`. This issue lists `Evaluate()` and
`CallFunction()`; the annotate path appears to build its error the same way. Worth
grepping for other `script exception: %s` constructions so one fix covers them all.

**Why this one is worth prioritising above its apparent severity.** Nothing is broken
functionally — but with the message stripped, every `eval` failure has to be diagnosed
by bisecting the script by hand. Concretely: I hit this on a redeclaration error, could
not see the cause, and concluded that `vibium eval` rejected multi-statement scripts. It
does not. That wrong conclusion reached a published article and three files before the
control probe above caught it. A one-line error string prevents that class of mistake
entirely.
