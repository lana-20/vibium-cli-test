# B24 — `vibium map` misses framework-attached click handlers

**vibium v26.5.31 · macOS darwin 25.5.0**
**Filed as:** _not yet filed_ — deferred upstream 2026-07-06 pending a stable repro page.
**This file supplies that repro.**

## Why it was deferred

The original repro, `blackboxpuzzles.workroomprds.com/puzzle29.html`, now returns **404**
(the site root still 200s). The 2026-06-01 run recorded `eval querySelectorAll("li")`
returning `[]` alongside the `map` failure — in hindsight that was the page already being

Re-tested from scratch on v26.5.31. **The bug is real, but the original description was
wrong.**

## The original description was inaccurate

B24 said `map` "only scans semantic interactive elements". It does not — it exposes
non-semantic elements fine, provided the clickability is declared in the static DOM:

```html
<li id="li-onclick" onclick="..." style="cursor:pointer">li with onclick</li>
<div id="div-role" role="button" tabindex="0">div with role</div>
```
```
@e1 [li] "li with onclick"
@e2 [div] "div with role=button + tabindex"
```

## What `map` actually detects — isolated signal matrix

Each element carries exactly one signal, nothing else:

| # | Signal on a bare `<div>` | `map` |
|---|---|---|
| 1 | inline `onclick` attribute | **exposed** |
| 2 | `style="cursor:pointer"` | missed |
| 3 | `role="button"` | **exposed** |
| 4 | `tabindex="0"` | **exposed** |
| 5 | `addEventListener('click', …)` | missed |
| 6 | `addEventListener` + `cursor:pointer` | missed |
| 7 | `addEventListener` + `role="button"` | **exposed** |
| 8 | nothing (negative control) | missed — correct |

**Accurate statement:** `map` infers clickability from *static DOM attributes only* —
semantic tag, `role`, `tabindex`, inline `onclick`. It cannot see handlers registered
with `addEventListener`, and does not treat `cursor:pointer` as an affordance.

That matters because **every modern framework attaches handlers via `addEventListener`**.
React, Vue and Svelte components rendered as `<div>`/`<li>`/`<span>` without an explicit
`role` are invisible to `map`.

Self-contained repro, no external site required:

```sh
vibium content --stdin <<'EOF'
<div id="s1" onclick="void 0">1 · inline onclick only</div>
<div id="s2" style="cursor:pointer">2 · cursor:pointer only</div>
<div id="s3" role="button">3 · role=button only</div>
<div id="s4" tabindex="0">4 · tabindex only</div>
<div id="s5">5 · addEventListener only</div>
<div id="s6" style="cursor:pointer">6 · addEventListener + cursor:pointer</div>
<div id="s7" role="button">7 · addEventListener + role=button</div>
<div id="s8" class="btn">8 · nothing at all</div>
<script>['s5','s6','s7'].forEach(id =>
  document.getElementById(id).addEventListener('click', () => {}));</script>
EOF
vibium map
```

## Replacement live repro — coffee-cart.app

A small, stable, auth-free Vue practice app already used across this suite. The nine
coffee cups are the site's primary interaction, and **not one of them appears in `map`**:

```sh
vibium go https://coffee-cart.app/
sleep 3
vibium map
# @e1 [a] "Menu page"
# @e2 [a] "Cart page"
# @e3 [a] "GitHub page"
# @e4 [button type="button"] "Proceed to checkout"
#   → 4 refs, zero products

vibium eval '(() => document.querySelectorAll(".cup").length)()'          # → 9
vibium map --selector ".list"                                             # → No interactive elements found
```

The cups are genuinely clickable — clicking one adds to the cart:

```sh
vibium eval '(() => { document.querySelectorAll(".cup")[2].click(); return "clicked"; })()'
# Total: $0.00 → Total: $19.00
```

And each cup carries **no** detectable signal:

```json
{"tag":"div","cls":"cup","cursor":"auto","role":null,"tabindex":null,"onclickAttr":false}
```

Note `cursor: auto` — even a `cursor:pointer` heuristic would not catch these, so this
site exercises the hardest case.

**There is a recovery path**, which is why this is P3 and not higher — a CSS selector
still resolves:

```sh
vibium find ".cup"      # → @e1 [div] "espresso"
```

So the defect is that `map` is *incomplete* as a discovery mechanism, not that the
elements are unreachable. For an agent driving the browser from `map` output alone —
the primary use case — a shopping site whose entire product grid is invisible is still a
serious gap.

## `cursor: pointer` is not a usable heuristic — measured

An earlier draft of this write-up proposed treating computed `cursor: pointer` as an
affordance. **Do not do this.** Measured on ui5.sap.com with CDP
`DOMDebugger.getEventListeners` as the oracle — the only reliable one, since
`addEventListener` is not introspectable from page JS:

| | count |
|---|---|
| visible non-semantic elements with `cursor: pointer` | 129 |
| …with their own click/mousedown/pointerdown listener | **0** |
| …with a delegated listener on an ancestor (≤6 levels) | 2 |
| …with no listener found at all | 127 |

And the reason is visible in what they are:

```
span.sapMLnkText            71    the text span inside a <a class="sapMLnk">
span.sapMBtnInner           27    the inner span of a <button>
div.sapMITBFilterWrapper     6    icon-tab-bar internals
span.sapMITHTextContent      6
div.sapMITBContentArrow      6
```

**127 of the 129 are descendants of elements `map` already exposes.** They inherit
`cursor: pointer` from the link or button that contains them. Only 2 are standalone, and
both are empty-text search-field decorations with no listener.

So the heuristic would roughly double the ref count on this page with duplicates pointing
at click targets already in the map — noise, not signal. It also would not help the actual
repro: coffee-cart's `.cup` divs compute `cursor: auto`.

## Suggested fix

**Introspect registered listeners.** On the evidence above this is not one option of two —
it is the only approach that works, because the visual affordance and the real handler are
uncorrelated in both directions: styled-but-not-a-target on ui5, target-but-unstyled on
coffee-cart.

Chrome DevTools uses CDP's `DOMDebugger.getEventListeners`, and it is demonstrably usable
here — the table above was produced with it via a CDP session, resolving each element to an
`objectId` and walking up to six ancestors for delegated handlers. Whether an equivalent is
reachable from vibium's WebDriver BiDi transport is a question for the maintainers; if it
is not, a CDP side-channel for discovery only may be worth considering, given `map` is the
primary interface for agent-driven use.

A cheaper partial step, if listener introspection is out of scope: expose elements that are
`cursor: pointer` **and** have no semantic ancestor. That cuts ui5's 129 to 2 and adds no
duplicates — but it still finds nothing on coffee-cart, so it does not close this bug.

**Cross-tool note.** Neither Playwright nor Selenium ships a `map` equivalent, so there is
no competitor behaviour to match here — this is a vibium-specific feature and the gap is
in its coverage, not in parity. Both of those tools would reach the cups only through a
CSS selector, which `vibium find ".cup"` already does.
