# B24 — `vibium map` misses framework-attached click handlers

**vibium v26.5.31 · macOS darwin 25.5.0** · source re-verified against `main` 2026-08-08
**Filed as:** _not yet filed_ — deferred upstream 2026-07-06 pending a stable repro page.
**This file supplies that repro.**

> **File this as an ENHANCEMENT, not a defect.** `mapScript`
> (`internal/agent/handlers.go`) queries a **fixed interactive-selector list** and applies
> exactly one filter, visibility. A plain `<div>` carrying no `role`, `tabindex` or
> `onclick` matches no term in that list, so `map` omitting it is that design working as
> written — not a filter bug. Framed as "`map` has a bug" this earns the same source-cited
> rebuttal that closed [#212](https://github.com/VibiumDev/vibium/issues/212)
> (*"the premise does not hold on either half"*). The defensible ask is that the
> **discovery strategy** cannot see behaviour attached via `addEventListener`, and that
> vibium already ships a BiDi-native signal that reaches these elements — see
> "`a11y-tree` already sees what `map` misses" below.

## Why it was deferred

The original repro, `blackboxpuzzles.workroomprds.com/puzzle29.html`, now returns **404**
(the site root still 200s). The 2026-06-01 run recorded `eval querySelectorAll("li")`
returning `[]` alongside the `map` failure — in hindsight that was the page already being
gone, not a discovery failure, so the original evidence was unsound.

Re-tested from scratch on v26.5.31. **The bug is real, but the original description was
wrong.**

## The original description was inaccurate

B24 said `map` "only scans semantic interactive elements". It does not — it exposes
non-semantic elements fine, provided the clickability is declared in the static DOM:

```html
<li id="li-onclick" onclick="..." style="cursor:pointer">li with onclick</li>
<div id="div-role" role="button" tabindex="0">div with role</div>
```
```
@e1 [li] "li with onclick"
@e2 [div] "div with role=button + tabindex"
```

## What `map` actually detects — isolated signal matrix

Each element carries exactly one signal, nothing else:

| # | Signal on a bare `<div>` | `map` |
|---|---|---|
| 1 | inline `onclick` attribute | **exposed** |
| 2 | `style="cursor:pointer"` | missed |
| 3 | `role="button"` | **exposed** |
| 4 | `tabindex="0"` | **exposed** |
| 5 | `addEventListener('click', …)` | missed |
| 6 | `addEventListener` + `cursor:pointer` | missed |
| 7 | `addEventListener` + `role="button"` | **exposed** |
| 8 | nothing (negative control) | missed — correct |

**Accurate statement:** `map` infers clickability from *static DOM attributes only* —
semantic tag, `role`, `tabindex`, inline `onclick`. It cannot see handlers registered
with `addEventListener`, and does not treat `cursor:pointer` as an affordance.

That matters because **every modern framework attaches handlers via `addEventListener`**.
React, Vue and Svelte components rendered as `<div>`/`<li>`/`<span>` without an explicit
`role` are invisible to `map`.

Self-contained repro, no external site required:

```sh
vibium content --stdin <<'EOF'
<div id="s1" onclick="void 0">1 · inline onclick only</div>
<div id="s2" style="cursor:pointer">2 · cursor:pointer only</div>
<div id="s3" role="button">3 · role=button only</div>
<div id="s4" tabindex="0">4 · tabindex only</div>
<div id="s5">5 · addEventListener only</div>
<div id="s6" style="cursor:pointer">6 · addEventListener + cursor:pointer</div>
<div id="s7" role="button">7 · addEventListener + role=button</div>
<div id="s8" class="btn">8 · nothing at all</div>
<script>['s5','s6','s7'].forEach(id =>
  document.getElementById(id).addEventListener('click', () => {}));</script>
EOF
vibium map
```

## Replacement live repro — coffee-cart.app

A small, stable, auth-free Vue practice app already used across this suite. The nine
coffee cups are the site's primary interaction, and **not one of them appears in `map`**:

```sh
vibium go https://coffee-cart.app/
sleep 3
vibium map
# @e1 [a] "Menu page"
# @e2 [a] "Cart page"
# @e3 [a] "GitHub page"
# @e4 [button type="button"] "Proceed to checkout"
#   → 4 refs, zero products

vibium eval '(() => document.querySelectorAll(".cup").length)()'          # → 9
vibium map --selector ".list"                                             # → No interactive elements found
```

The cups are genuinely clickable — clicking one adds to the cart:

```sh
vibium eval '(() => { document.querySelectorAll(".cup")[2].click(); return "clicked"; })()'
# Total: $0.00 → Total: $19.00
```

And each cup carries **no** detectable signal:

```json
{"tag":"div","cls":"cup","cursor":"auto","role":null,"tabindex":null,"onclickAttr":false}
```

Note `cursor: auto` — even a `cursor:pointer` heuristic would not catch these, so this
site exercises the hardest case.

**There are recovery paths**, which is why this is P3 and not higher. Both a CSS selector
and a text lookup resolve:

```sh
vibium find ".cup"              # → @e1 [div] "espresso"
vibium find text "Espresso"     # → @e1 [h4] "Espresso $10.00"   (the label, not the cup)
```

Note the text form lands on the price heading rather than the clickable `.cup` div, so it
is a workaround with a caveat rather than a clean substitute. The a11y tree mentions the
product once but does not expose the cups as interactive nodes.

So the defect is that `map` is *incomplete* as a discovery mechanism, not that the elements
are unreachable. For an agent driving the browser from `map` output alone — the primary use
case — a shopping site whose entire product grid is invisible is still a serious gap.

## `cursor: pointer` is not a usable heuristic — measured

An earlier draft of this write-up proposed treating computed `cursor: pointer` as an
affordance. **Do not do this.** Measured on ui5.sap.com with CDP
`DOMDebugger.getEventListeners` as the oracle — the only reliable one, since
`addEventListener` is not introspectable from page JS:

| | count |
|---|---|
| visible non-semantic elements with `cursor: pointer` | 129 |
| …with their own click/mousedown/pointerdown listener | **0** |
| …with a delegated listener on an ancestor (≤6 levels) | 2 |
| …with no listener found at all | 127 |

And the reason is visible in what they are:

```
span.sapMLnkText            71    the text span inside a <a class="sapMLnk">
span.sapMBtnInner           27    the inner span of a <button>
div.sapMITBFilterWrapper     6    icon-tab-bar internals
span.sapMITHTextContent      6
div.sapMITBContentArrow      6
```

**127 of the 129 are descendants of elements `map` already exposes.** They inherit
`cursor: pointer` from the link or button that contains them. Only 2 are standalone, and
both are empty-text search-field decorations with no listener.

So the heuristic would roughly double the ref count on this page with duplicates pointing
at click targets already in the map — noise, not signal. It also would not help the actual
repro: coffee-cart's `.cup` divs compute `cursor: auto`.

## `a11y-tree` already sees what `map` misses — and over the same transport

Measured on coffee-cart.app, v26.5.31, 2026-08-08:

| | result |
|---|---|
| `vibium map` | 4 refs — 3 nav links + checkout. **0 of the 9 products.** |
| `vibium a11y-tree` | **all 9 products, each as a named node** |

```
vibium a11y-tree | grep -o '"role":"generic","name":"[^"]*"'
#  "role":"generic","name":"Espresso"
#  "role":"generic","name":"Espresso Macchiato"
#  "role":"generic","name":"Cappuccino"        … 9 products in total
```

The signal `a11y-tree` is reading is on the element itself:

```
{"tag":"DIV","role":null,"tabindex":null,"onclick":false,"cursor":"auto","ariaLabel":"Espresso"}
```

No `role`, no `tabindex`, no inline `onclick`, `cursor: auto` — **but a real
`aria-label`**, which becomes the accessible name. So the page is not signal-free; `map`
is looking at a set of signals that happens to exclude the one present here.

**This is not a transport question.** `A11yTree` (`internal/api/handlers_a11y.go:140`)
and `mapScript` (`internal/agent/handlers.go`) are sibling injected-JS functions over the
**identical** `script.callFunction` BiDi call. `A11yTreeScript()` already computes roles
and accessible names, including implicit roles, entirely in page JS. Whatever `map` would
need is already implemented, in the same codebase, over the same plumbing — no CDP, no new
capability.

**Stated limit, so this is not overclaimed:** the cups' accessible role is `generic`, not
`button` or `link`. `a11y-tree` therefore establishes that they are *named and present*,
**not** that they are interactive. A strict role-based reading of "map interactive
elements" would legitimately skip them. The ask is not "trust the a11y role" — it is that
`map` currently returns *nothing at all* for the page's primary interaction target, while
two sibling commands (`a11y-tree`, `find`) both reach it.

## Suggested fix

**Preferred, and already in-tree: fall back to the accessibility signal.** When an element
matches no term in the interactive selector list, consult the accessible name/role the way
`A11yTreeScript()` already does. Both run as injected JS over the same
`script.callFunction` call, so this needs no new transport, no CDP, and no capability that
is not already shipping. On coffee-cart this surfaces all 9 products; the `generic` role
means a role-based gate would have to be deliberately relaxed for named-but-unroled
elements, which is the design decision worth discussing on the issue.

**Fuller, but a transport question: introspect registered listeners.** The visual
affordance and the real handler are uncorrelated in both directions — styled-but-not-a-target
on ui5, target-but-unstyled on coffee-cart — so listener introspection is the only approach
that closes the gap completely. Chrome DevTools uses CDP's `DOMDebugger.getEventListeners`,
and the signal matrix above was produced with it via a CDP session. **Noted only as
context:** `clicker/` contains no CDP usage anywhere today (verified against `main`
2026-08-08), so this would mean a new side-channel — a much larger ask than the fallback
above, and entirely the maintainers' call.

A cheaper partial step, if listener introspection is out of scope: expose elements that are
`cursor: pointer` **and** have no semantic ancestor. That cuts ui5's 129 to 2 and adds no
duplicates — but it still finds nothing on coffee-cart, so it does not close this bug.

**Cross-tool note.** Neither Playwright nor Selenium ships a `map` equivalent, so there is
no competitor behaviour to match — this is a vibium-specific feature and the gap is in its
coverage, not in parity.

Measured on coffee-cart for context, since an earlier draft of this file wrongly claimed
those tools could only reach the cups by CSS selector:

| Playwright locator | matches |
|---|---|
| `locator('.cup')` | 9 |
| `getByRole('button')` | 1 |
| `getByRole('link')` | 3 |
| `getByText('Espresso')` | 12 |
| `ariaSnapshot()` mentions the product | yes |

Role-based lookup does not find the cups — consistent with them having no `role` — but text
lookup does, and so does vibium's own `find text`. The cups are reachable by several routes
in every tool; `map` is the one that misses them.
